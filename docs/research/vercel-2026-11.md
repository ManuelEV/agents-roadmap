## 2. Modelos a través de AI Gateway

### Cómo se escribe un modelo
- Formato `"proveedor/modelo"`, por ejemplo `"anthropic/claude-sonnet-5.5"`.
- En el AI SDK, AI Gateway es el **proveedor global por defecto**: un string en `model` ya pasa por el gateway. Equivalentes: `import { gateway } from 'ai'` → `gateway('anthropic/claude-sonnet-5.5')`, o `import { gateway } from '@ai-sdk/gateway'`. Instancia propia: `createGateway({ apiKey, teamIdOrSlug, baseURL, headers, fetch })` desde `ai`.
- Para usar un proveedor directo: `pnpm add @ai-sdk/openai` y `model: openai('gpt-6-astra')`.
- Lista viva de ids y precios, sin API key: `https://ai-gateway.vercel.sh/v1/models` (507 modelos el 2026-11-15; 322 de tipo `language`).
- El gateway también expone APIs compatibles: OpenAI Chat Completions (`https://ai-gateway.vercel.sh/v1/chat/completions`), OpenAI Responses (`/v1/responses`) y Anthropic Messages (`/v1/messages`). No hace falta desplegar en Vercel para usarlo.

### Autenticación
Orden de precedencia en el AI SDK (https://vercel.com/docs/ai-gateway/authentication-and-byok/oidc):
1. `apiKey` pasada a `createGateway()`.
2. Variable de entorno `AI_GATEWAY_API_KEY`.
3. Token OIDC de Vercel (automático en despliegues; se refresca solo).

Una API key no vacía siempre gana sobre OIDC, aunque sea inválida. Para usar OIDC en un despliegue, quitar `AI_GATEWAY_API_KEY` del proyecto. En local: `vercel link` y `vercel env pull` (escribe `VERCEL_OIDC_TOKEN`, válido 12 horas; volver a correr `vercel env pull` para renovarlo, o usar `vercel dev`, que lo renueva solo). Sin key ni OIDC: error `GatewayAuthenticationError`.

### Precio del gateway
- "AI Gateway charges no markup and no platform fee on tokens": se paga el precio de lista del proveedor, con **AI Gateway Credits** prepagados. Las comisiones de procesamiento de pago corren por cuenta del usuario.
- Hay nivel gratuito (crédito mensual incluido, solo un subconjunto de modelos, con límites por modelo más bajos → `429`) y nivel pagado (al comprar créditos; el gateway no aplica rate limits propios, solo los del proveedor).
- **BYOK**: se configura en los ajustes de AI Gateway del equipo, sin cambios de código; sin markup. Requiere nivel pagado y saldo positivo. Si la llamada con tu key falla, el gateway reintenta con las keys de Vercel y eso sí se cobra a tus créditos.
- Presupuestos (budgets) por equipo, proyecto, API key o miembro: al superarlos el gateway responde `402`. No cuentan el gasto BYOK.
- Recargos opcionales: Custom Reporting ($0.075 por 1,000 escrituras, $5 por 1,000 consultas), allowlist de proveedores a nivel equipo ($0.10 por 1,000 requests; Pro/Enterprise), ZDR a nivel equipo ($0.10 por 1,000 requests), Regional Hosting (beta, 5% del costo de inferencia).

### Ruteo y fallbacks (`providerOptions.gateway`)
Sin opciones, el gateway elige proveedor por uptime y latencia recientes y cae a otros proveedores del mismo modelo. Opciones verificadas:

| Opción | Tipo | Efecto |
|---|---|---|
| `order` | `string[]` | Orden de proveedores a intentar (slugs como `'bedrock'`, `'anthropic'`, `'vertex'`). |
| `only` | `string[]` | Restringe a esos proveedores; si fallan, la request falla (no hay fallback fuera de la lista). |
| `sort` | `'cost' \| 'ttft' \| 'tps'` | Ordena proveedores por costo, tiempo al primer token o tokens por segundo. |
| `models` | `string[]` | Modelos de respaldo, en orden, si el primario falla o no está disponible. |
| `user` | `string` | Id de usuario final para atribución de gasto. |
| `tags` | `string[]` | Etiquetas para reportes. |

También existen `zeroDataRetention`, `disallowPromptTraining` y `has` (por ejemplo `has: ['tool-use']`, `has: ['implicit-caching']`) como filtros. La página general del gateway menciona además `caching: 'auto'` para prompt caching entre proveedores (ubicación exacta de la opción: a confirmar).

```ts
// https://vercel.com/docs/ai-gateway/models-and-providers/model-fallbacks
import { generateText } from 'ai';

const { text } = await generateText({
  model: 'anthropic/claude-fable-5',
  prompt: 'Write a haiku about TypeScript.',
  providerOptions: {
    gateway: {
      models: ['anthropic/claude-opus-5', 'google/gemini-3.1-pro-preview'],
    },
  },
});
```

El gateway trae tools ejecutadas por el propio gateway, usables con cualquier modelo: `gateway.tools.perplexitySearch()`, y también Exa Search, Browserbase Search/Fetch, Tako Search y Parallel Search (https://ai-sdk.dev/providers/ai-sdk-providers/ai-gateway).

## 3. AI SDK Core para agentes (API real de v7)

### Instalación y requisitos

- `.env.local`: `AI_GATEWAY_API_KEY=xxxxxxxxx`.
- **Node.js 22 o superior** (probado en 22, 24 y 26; la guía recomienda 24 LTS o 26 para producción). **Solo ESM**: `require()` ya no funciona; usar `"type": "module"` o `.mjs`.
- Versiones (npm, 2026-11-15): `ai` 7.0.173 · `@ai-sdk/react` 4.0.177 · `@ai-sdk/gateway` 4.0.146 · `@ai-sdk/openai` 4.0.118 · `@ai-sdk/anthropic` 4.0.105 · `@ai-sdk/google` 4.0.121 · `@ai-sdk/mcp` 2.0.99 · `@ai-sdk/otel` 1.0.173 · `@ai-sdk/devtools` 1.0.76 · `@ai-sdk/workflow` 2.0.105 · `@ai-sdk/tui` 1.0.174 · `zod` 4.6.7.
- Migración desde v6: `npx @ai-sdk/codemod v7`, o el skill `npx skills add vercel/ai --skill migrate-ai-sdk-v6-to-v7`.
- Versionado: las APIs con prefijo `experimental_` pueden cambiar en cualquier release; la doc pide fijar la versión exacta si se usan.

### `generateText` / `streamText`
- `generateText`: no interactivo (automatizaciones, agentes sin UI). `streamText`: interactivo (chat).
- Prompt: `prompt` (string) o `messages` (`ModelMessage[]`), más `instructions` (antes `system`).
- Resultado de `generateText`: `content`, `text` (del último paso), `toolCalls` y `toolResults` (de todos los pasos), `finishReason`, `usage` (total de todos los pasos), `steps`, `finalStep`, `output`, `responseMessages`, `warnings`. `totalUsage` quedó deprecado (usar `usage`); el uso del último paso es `finalStep.usage`.
- `streamText`: `result.stream` (todas las partes; antes `fullStream`), `result.textStream`, y promesas como `await result.finalStep`, `await result.responseMessages`.
- Callbacks: `onStart`, `onStepStart`, `onToolExecutionStart`, `onToolExecutionEnd`, `onStepEnd`, `onEnd`; en `streamText` además `onChunk` y `onError`.

### Definir una tool
```ts
// https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling
import { z } from 'zod';
import { generateText, tool, isStepCount } from 'ai';

const { text, steps } = await generateText({
  model: "anthropic/claude-sonnet-5.5",
  tools: {
    weather: tool({
      description: 'Get the weather in a location',
      inputSchema: z.object({
        location: z.string().describe('The location to get the weather for'),
      }),
      execute: async ({ location }) => ({
        location,
        temperature: 72 + Math.floor(Math.random() * 21) - 10,
      }),
    }),
  },
  stopWhen: isStepCount(5), // stop after a maximum of 5 steps if tools were called
  prompt: 'What is the weather in San Francisco?',
});
```
- Campos de una tool: `description` (opcional; string o función), **`inputSchema`** (Zod o JSON Schema; es el nombre vigente, `parameters` es de v4), `execute` (opcional: sin `execute` la llamada se reenvía al cliente o detiene el loop), `strict` (opcional), `contextSchema` (contexto tipado por tool) y `outputSchema` en tools MCP.
- Segundo argumento de `execute`: `{ toolCallId, messages, abortSignal, context, experimental_sandbox }`.
- Cuatro tipos de tools: **function tools** (`tool()`), **dynamic tools** (`dynamicTool()`, input `unknown`), **provider-defined** (el proveedor define el esquema y tú ejecutas, por ejemplo `anthropic.tools.bash_20250124({ execute })`) y **provider-executed** (corren en el proveedor, por ejemplo `openai.tools.webSearch()`).
- `toolChoice`: `'auto'` (defecto), `'required'`, `'none'` o `{ type: 'tool', toolName }`. `activeTools` limita las tools visibles.

### Control del loop
- `stopWhen` solo se evalúa cuando el último paso tiene resultados de tools. Condiciones incluidas: `isStepCount(n)`, `hasToolCall(...nombres)`, `isLoopFinished()` (nunca dispara: corre hasta que el modelo termina). Acepta un arreglo (se detiene con cualquiera) o una función `StopCondition<typeof tools>` propia que recibe `{ steps }`.
- **Defaults distintos**: `generateText` / `streamText` → `isStepCount(1)` (un solo paso). `ToolLoopAgent` → `isStepCount(20)`, y registra un warning si ese límite por defecto corta el loop. `WorkflowAgent.stream()` → sin límite.
- El loop termina cuando: el modelo devuelve un finish reason distinto de tool-calls, se llama una tool sin `execute`, una tool call necesita aprobación, o se cumple una condición.
- `prepareStep({ model, stepNumber, steps, messages, initialMessages, responseMessages, runtimeContext })` corre antes de cada paso y puede devolver: `model`, `activeTools`, `toolChoice`, `messages`, `instructions`, `experimental_sandbox` y ajustes como `temperature`, `maxOutputTokens`, `topP`, `topK`, `seed`, `stopSequences`, `reasoning`. Ojo: en v7 un `messages` devuelto **persiste** como base de los pasos siguientes; los ajustes de modelo aplican solo a ese paso.
- Compactación: `pruneMessages({ messages, reasoning: 'all', toolCalls: 'before-last-3-messages', emptyMessages: 'remove' })` dentro de `prepareStep`.
- Steering (experimental): `experimental_createSteering()` + `steering.steer('...')` / `steering.queue('...')` para inyectar mensajes del usuario en un loop en curso.

### La clase de agente: ejemplo mínimo completo
```ts
// https://ai-sdk.dev/docs/agents/overview
import { ToolLoopAgent, tool } from 'ai';
import { z } from 'zod';

const weatherAgent = new ToolLoopAgent({
  model: "anthropic/claude-sonnet-5.5",
  tools: {
    weather: tool({
      description: 'Get the weather in a location (in Fahrenheit)',
      inputSchema: z.object({
        location: z.string().describe('The location to get the weather for'),
      }),
      execute: async ({ location }) => ({
        location,
        temperature: 72 + Math.floor(Math.random() * 21) - 10,
      }),
    }),
    convertFahrenheitToCelsius: tool({
      description: 'Convert temperature from Fahrenheit to Celsius',
      inputSchema: z.object({
        temperature: z.number().describe('Temperature in Fahrenheit'),
      }),
      execute: async ({ temperature }) => {
        const celsius = Math.round((temperature - 32) * (5 / 9));
        return { celsius };
      },
    }),
  },
});

const result = await weatherAgent.generate({
  prompt: 'What is the weather in San Francisco in celsius?',
});

console.log(result.text); // agent's final answer
console.log(result.steps); // steps taken by the agent
```
Opciones del constructor (acepta los mismos ajustes que `generateText`/`streamText`): `model`, `instructions`, `tools`, `stopWhen`, `toolChoice`, `output`, `prepareStep`, `toolApproval`, `runtimeContext` (estado compartido del loop), `toolsContext` (valores por tool, por ejemplo API keys, declarados con `contextSchema`), `callOptionsSchema` + `prepareCall` (contexto que cambia por invocación), `telemetry` y los callbacks de ciclo de vida (si se definen en constructor y en la llamada, corren ambos, primero el del constructor).

Tres formas de usarlo: `agent.generate({ prompt | messages })`, `agent.stream({ prompt })` (iterar `result.textStream`) y, para UI, `createAgentUIStreamResponse({ agent, uiMessages })`. Tipado de mensajes: `InferAgentUIMessage<typeof agent>`. Terminal: `runAgentTUI({ title, agent })` de `@ai-sdk/tui`.

Sub-agentes: una tool cuyo `execute` llama a otro `ToolLoopAgent`; `toModelOutput` controla qué ve el modelo padre. Las tools de sub-agentes no pueden usar `toolApproval` (https://ai-sdk.dev/docs/agents/subagents).

### Salida estructurada
```ts
// https://ai-sdk.dev/docs/agents/building-agents
import { ToolLoopAgent, Output } from 'ai';
import { z } from 'zod';

const analysisAgent = new ToolLoopAgent({
  model: "anthropic/claude-sonnet-5.5",
  output: Output.object({
    schema: z.object({
      sentiment: z.enum(['positive', 'neutral', 'negative']),
      summary: z.string(),
      keyPoints: z.array(z.string()),
    }),
  }),
});

const { output } = await analysisAgent.generate({
  prompt: 'Analyze customer feedback from the last quarter',
});
```
La doc estandariza la salida estructurada en la propiedad `output` de `generateText`/`streamText` (`Output.object()`, `Output.array()`), combinable con tools en la misma request. Generar la salida estructurada **cuenta como un paso**: tenerlo en cuenta en `stopWhen`.

### Forma real de pasos, tool calls y tool results
- `result.steps[i]`: `text`, `toolCalls`, `toolResults`, `finishReason`, `usage` (`inputTokens`, `outputTokens`, `totalTokens`), `performance` (`stepTimeMs`, `responseTimeMs`, `toolExecutionMs`, `effectiveOutputTokensPerSecond`…), `response.messages`.
- Tool call: `{ toolCallId, toolName, input, dynamic? }`. Con tools estáticas `input` está tipado; si `toolCall.dynamic` es true, `input` es `unknown`.
- Parte tool-result en mensajes: `{ type: 'tool-result', toolCallId, toolName, output }`.
- En `onToolExecutionEnd`: `{ toolCall, toolExecutionMs, toolOutput }`, donde `toolOutput.type` es `'tool-result'` (con `output`) o `'tool-error'` (con `error`).
- `result.staticToolCalls`: tool calls no ejecutadas (patrón de tool `done` sin `execute` + `toolChoice: 'required'`).
- Historial: `messages.push(...result.responseMessages)` (en `streamText`: `await result.responseMessages`).
- Tipos auxiliares: `ToolSet`, `TypedToolCall<typeof tools>`, `TypedToolResult<typeof tools>`, `ModelMessage`, `UIMessage`.

### Aprobación de tools (human-in-the-loop)
El mecanismo vigente es **`toolApproval`** en `ToolLoopAgent`, `generateText` o `streamText`. `needsApproval` en `tool()` quedó **deprecado** en v7 para esos tres (sigue soportado en `WorkflowAgent`, donde `toolApproval` tiene precedencia).

```ts
// https://ai-sdk.dev/docs/agents/tool-approvals
import { ToolLoopAgent, tool } from 'ai';
import { z } from 'zod';

const agent = new ToolLoopAgent({
  model: "anthropic/claude-sonnet-5.5",
  tools: {
    processPayment: tool({
      inputSchema: z.object({
        amount: z.number(),
        recipient: z.string(),
      }),
      execute: async ({ amount, recipient }) =>
        processPayment({ amount, recipient }),
    }),
  },
  toolApproval: {
    processPayment: async ({ amount }, { runtimeContext }) => {
      if (runtimeContext.role !== 'admin') {
        return { type: 'denied', reason: 'Only admins can send payments' };
      }
      return amount > 1000 ? 'user-approval' : undefined;
    },
  },
});
```
- Estados: `'not-applicable'` (defecto; `undefined` equivale), `'approved'`, `'denied'`, `'user-approval'`. Forma de objeto con motivo: `{ type: 'denied', reason }`.
- `toolApproval` puede ser un mapa por tool (string o función) o una sola función para todas (`({ toolCall, tools, toolsContext, messages, runtimeContext }) => ...`).
- Flujo manual: la primera llamada devuelve una parte `tool-approval-request` (con `approvalId`) en `result.content`; se agrega un mensaje `{ role: 'tool', content: [{ type: 'tool-approval-response', approvalId, approved, reason }] }` y se vuelve a llamar al agente.
- Seguridad: en el patrón estándar de `useChat` el historial lo manda el cliente, así que una aprobación podría falsificarse. Para tools sensibles usar `experimental_toolApprovalSecret: process.env.TOOL_APPROVAL_SECRET` (firma HMAC del nombre de la tool, el id y los argumentos; generar con `openssl rand -base64 32`; el mismo secreto en todas las instancias).
- No aplica a tools ejecutadas por el proveedor.
- Reglas como código: `@ai-sdk/policy-opa` (https://ai-sdk.dev/docs/agents/policy-tool-approvals; no se revisó en detalle).

### Harnesses y sandbox dentro del SDK
- `HarnessAgent` usa un adaptador (por ejemplo `@ai-sdk/harness-claude-code`) y una **sesión** que es dueña del estado: `const session = await agent.createSession()` y luego `agent.generate({ session, prompt })`. Devuelve los mismos tipos que `generateText`/`streamText`, así que se puede pasar a `toUIMessageStream` y a `useChat`. Adaptadores anunciados en el changelog: Claude Code, Codex, Pi, Deep Agents, OpenCode, Cline, Cursor, GitHub Copilot, Grok Build, fx y harnesses compatibles con ACP.
- `experimental_sandbox`: valor por llamada (`agent.generate({ prompt, experimental_sandbox })`) que llega al segundo argumento de `execute`. Pasarlo no aísla la tool por sí solo: la tool debe delegar explícitamente (`experimental_sandbox.run({ command, workingDirectory, abortSignal })`), y la descripción del sandbox no se agrega sola al prompt.

## 4. AI SDK UI

### `useChat` (API vigente)
- `import { useChat } from '@ai-sdk/react'`. Devuelve `messages`, `sendMessage`, `status`, `stop`, `regenerate`, `setMessages`, `error`, `addToolOutput`, `addToolApprovalResponse`. **No maneja el input**: se usa `useState` propio.
- `status`: `submitted`, `streaming`, `ready`, `error`.
- Transporte: por defecto `POST /api/chat`. Equivale a `transport: new DefaultChatTransport({ api: '/api/chat' })` (importado de `ai`), que acepta `headers`, `credentials` y `prepareSendMessagesRequest`. Existen también `TextStreamChatTransport` y `WorkflowChatTransport`.
- Cada mensaje tiene `id`, `role` y **`parts`** (ordenadas). Tipos de parte verificados en ejemplos de la doc: `text`, `tool-{nombreDeLaTool}` (tools estáticas, tipadas), `dynamic-tool` (tools dinámicas, con `part.toolName`), `step-start`, `steering-message` y `source-url`. Hay más (razonamiento, archivos, datos personalizados); sus nombres exactos como partes de `UIMessage` no se verificaron (ver "A confirmar").
- Estados de una parte de tool (`part.state`): `input-streaming`, `input-available`, `approval-requested`, `approval-responded`, `output-available`, `output-error`, `output-denied`. Campos: `part.toolCallId`, `part.input`, `part.output`, `part.errorText`, `part.approval` (`id`, `isAutomatic`, `requestReason`, `reason`).
- Tools del lado cliente: callback `onToolCall({ toolCall })` + `addToolOutput({ tool, toolCallId, output })` (sin `await`, para evitar deadlocks; revisar `toolCall.dynamic` primero). Reenvío automático: `sendAutomaticallyWhen: lastAssistantMessageIsCompleteWithToolCalls` o, con aprobaciones, `lastAssistantMessageIsCompleteWithApprovalResponses`.
- Frameworks: React (`@ai-sdk/react`), Vue (`@ai-sdk/vue`), Svelte (`@ai-sdk/svelte`), Angular (`@ai-sdk/angular`); SolidJS es comunitario.

Cada evento es `data: {json}` y el stream termina con `data: [DONE]`. Un backend propio debe enviar el header `x-vercel-ai-ui-message-stream: v1`. Tipos (https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol):

```
data: {"type":"start-step"}
data: {"type":"text-start","id":"msg_..."}
data: {"type":"text-delta","id":"msg_...","delta":"Hello"}
data: {"type":"text-end","id":"msg_..."}
data: {"type":"tool-input-start","toolCallId":"call_...","toolName":"getWeatherInformation"}
data: {"type":"tool-input-delta","toolCallId":"call_...","inputTextDelta":"San Francisco"}
```

## 5. Memoria y estado

**Lo que el SDK no da**: persistencia. En el patrón estándar de `useChat`, el servidor reconstruye la conversación con los mensajes que manda el cliente en cada turno y no guarda estado entre requests. `ToolLoopAgent` corre entero en memoria: si el proceso muere, se pierde el progreso.

Patrones recomendados por la doc:
- **Guardar `UIMessage[]`** (no `ModelMessage[]`) en tu propia base, en el `onEnd` de `toUIMessageStream({ stream: result.stream, originalMessages: messages, onEnd: ({ messages }) => saveChat({ chatId, messages }) })` (https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-message-persistence).
- **Validar al cargar** mensajes con tools, metadata o data parts: `validateUIMessages({ messages, tools, metadataSchema, dataSchemas })`.
- **Enviar solo el último mensaje**: `prepareSendMessagesRequest({ messages, id }) { return { body: { message: messages[messages.length - 1], id } }; }` y cargar el resto en el servidor.
- **Desconexión del cliente**: `consumeStream` quita la contrapresión para que la respuesta se guarde aunque el cliente se haya ido.
- **Streams reanudables**: opción `resume` de `useChat` + callback `consumeSseStream` + paquete `resumable-stream` (2.2.13) con Redis. Tú construyes: almacenamiento del stream activo por chat, Redis, un `POST` que crea el stream (`createResumableStreamContext({ waitUntil: after }).createNewResumableStream(streamId, () => stream)`) y un `GET /api/chat/[id]/stream` que lo reanuda (`resumeExistingStream`, con `UI_MESSAGE_STREAM_HEADERS`; responde 204 si no hay stream activo). En este esquema `stop()` solo corta la conexión; para detener la generación hace falta un endpoint propio (https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-resume-streams).

Memoria de largo plazo (https://ai-sdk.dev/docs/agents/memory) — tres enfoques:

| Enfoque | Ejemplo | Costo |
|---|---|---|
| Tool definida por el proveedor | `anthropic.tools.memory_20250818({ execute })`: Claude maneja un directorio `/memories` con comandos `view`, `create`, `str_replace`, `insert`, `delete`, `rename`; tú implementas el almacenamiento. | Atado a Anthropic. |
| Proveedores de memoria | Letta (`@letta-ai/vercel-ai-sdk-provider`), Mem0 (`@mem0/vercel-ai-provider`), Supermemory (`@supermemory/tools`), Hindsight (`@vectorize-io/hindsight-ai-sdk`), MongoDB (`@mongodb-developer/vercel-ai-memory`, apunta a AI SDK v6), Redis Agent Memory (`@redis/vercel-ai-sdk`, requiere AI SDK 7). | Dependencia externa y menos visibilidad. |
| Tool propia | Acciones estructuradas o un bash en sandbox sobre archivos. | Más trabajo, control total. |

Ninguno es de Vercel: **no hay un servicio de memoria administrado de primera parte para el AI SDK**. (eve sí trae memoria persistente entre sesiones, con Supermemory, un proveedor de archivos incluido o uno propio.)

## 6. Agentes durables y de larga duración

### Workflow SDK: API
`pnpm i workflow` (o `npm i workflow`). En Next.js se envuelve la config (https://workflow-sdk.dev/docs/getting-started/next):
```ts
// next.config.ts
import { withWorkflow } from "workflow/next";
import type { NextConfig } from "next";

const nextConfig: NextConfig = {};

export default withWorkflow(nextConfig);
```
Si hay `proxy.ts` (antes `middleware.ts`), excluir `.well-known/workflow/` del matcher.

Cuatro abstracciones (https://vercel.com/docs/workflows/concepts):
- **Workflow**: función con la directiva `'use workflow'`; orquesta, es determinista y se reproduce desde un log de eventos.
- **Step**: función con `'use step'`; unidad de trabajo con reintentos automáticos (3 intentos por defecto, según la doc de `WorkflowAgent`). `FatalError` (de `workflow`) evita el reintento.
- **Sleep**: `await sleep('7 days')` (o `sleep("5s")`), sin consumir cómputo.
- **Hook**: espera un evento externo. `defineHook<T>()` → `hook.create({ token })` dentro del workflow y `hook.resume(token, data)` desde una ruta. También `createHook()` y `createWebhook()` (genera una URL; `const request = await webhook`).
- Iniciar: `import { start } from 'workflow/api'` → `const run = await start(miWorkflow, [args])`; `run.readable` es el stream de salida. Streams: `getWritable()` de `workflow`.
- Inspección: `npx workflow inspect runs`, `npx workflow web`, `npx workflow inspect run <run-id> --decrypt`.

```ts
// https://vercel.com/docs/workflows/concepts
import { defineHook } from 'workflow';

// Human approval for AI-generated drafts
export const approvalHook = defineHook<{
  decision: 'approved' | 'changes';
  notes?: string;
}>();

export async function aiApprovalWorkflow(topic: string) {
  'use workflow';

  const draft = await generateDraft(topic);

  // Wait for human approval events
  const events = approvalHook.create({
    token: 'draft-123',
  });

  for await (const event of events) {
    if (event.decision === 'approved') {
      await publishDraft(draft);
      break;
    } else {
      const revised = await refineDraft(draft, event.notes);
      await publishDraft(revised);
    }
  }
}
```

```ts
// workflow/agent-chat.ts — https://ai-sdk.dev/docs/agents/workflow-agent
import { WorkflowAgent, type ModelCallStreamPart } from '@ai-sdk/workflow';
import { convertToModelMessages, tool, type UIMessage } from 'ai';
import { getWritable } from 'workflow';
import { z } from 'zod';

export async function chat(messages: UIMessage[]) {
  'use workflow';

  const modelMessages = await convertToModelMessages(messages);

  const agent = new WorkflowAgent({
    model: 'anthropic/claude-sonnet-5.5',
    instructions: 'You are a flight booking assistant.',

        description: 'Search for available flights',
        inputSchema: z.object({
          origin: z.string(),
          destination: z.string(),
          date: z.string(),
        }),
        execute: searchFlightsStep,
      }),
    },
  });

  const result = await agent.stream({
    messages: modelMessages,
    writable: getWritable<ModelCallStreamPart>(),
  });

  return { messages: result.messages };
}

async function searchFlightsStep(input: {
  origin: string;
  destination: string;
  date: string;

  const response = await fetch(`https://api.flights.example/search?...`);
```

```ts
// app/api/chat/route.ts — misma página
import { createModelCallToUIChunkTransform } from '@ai-sdk/workflow';
import { createUIMessageStreamResponse, type UIMessage } from 'ai';
import { start } from 'workflow/api';
import { chat } from '@/workflow/agent-chat';

export async function POST(request: Request) {
  const { messages }: { messages: UIMessage[] } = await request.json();

  const run = await start(chat, [messages]);

  return createUIMessageStreamResponse({
    stream: run.readable.pipeThrough(createModelCallToUIChunkTransform()),
  });
}
```
Diferencias con `ToolLoopAgent` que hay que enseñar:
- Paquete `@ai-sdk/workflow`; **no implementa la interfaz `Agent`**, así que no sirve con `createAgentUIStreamResponse`.
- `stream()` es la API principal y **no tiene límite de pasos por defecto** (definir `stopWhen: isStepCount(n)`); `generate()` sí corta a los 20.
- `stream()` recibe `ModelMessage[]` (convertir con `convertToModelMessages`) y escribe `ModelCallStreamPart` en un `writable`; en el borde se convierte con `createModelCallToUIChunkTransform()`.
- Las tools con `'use step'` son pasos durables con reintentos; sin `'use step'` corren en memoria sin garantías.
- Aprobación: `needsApproval: true` en la tool o `toolApproval` en el agente; el workflow se suspende hasta la respuesta. Secreto de firma como `{ environmentVariable: 'TOOL_APPROVAL_SECRET' }`.
- `runtimeContext` y `toolsContext` deben ser serializables. `WorkflowChatTransport` reconecta el stream si se corta.
- Migración desde `DurableAgent`: cambiar `import { DurableAgent } from 'workflow/ai'` por `import { WorkflowAgent } from '@ai-sdk/workflow'`; `maxSteps` → `stopWhen`; `experimental_output` → `output`.

Cuándo usar cada cosa (según https://ai-sdk.dev/docs/agents/eve): `ToolLoopAgent` para un loop dentro de una app; `WorkflowAgent` cuando se necesita ejecución durable y reanudable con pasos explícitos; eve cuando se quiere un agente de producción completo (canales, cron, aprobaciones, memoria, `eve eval`) sin armar las piezas. eve: `npx eve@latest init my-agent`; estructura `agent/instructions.md`, `agent/tools/*.ts` (`defineTool`), `agent/agent.ts` (`defineAgent({ model, reasoning })`).

### Despliegue, precios y límites
- El mismo código corre en local (Local World, datos en `.workflow-data/`), en Vercel sin configuración (Vercel World) o en otra infraestructura con un "World" (por ejemplo `@workflow/world-postgres`; variable `WORKFLOW_TARGET_WORLD`). Desplegar: `vercel deploy`.
- **Requisito**: activar "Enable access to System Environment Variables" en el proyecto; sin eso el despliegue cae al Local World y los runs fallan.
- En Vercel: las Functions ejecutan el código, Vercel Queues encola, y hay persistencia administrada. Cada run queda fijado a una región; por defecto los runs siguen en el despliegue donde nacieron (skew protection). Payloads cifrados de extremo a extremo (AES-256-GCM) sin configuración.
- Frameworks con guía: Next.js, Vite, React Router, Astro, Express, Fastify, Hono, Nitro, Nuxt, SvelteKit, TanStack Start; NestJS en beta. Python (SDK `vercel`) en beta.

Precios de Vercel Workflows (https://vercel.com/docs/workflow/pricing):

| Recurso | Incluido en Hobby | Bajo demanda |
|---|---|---|
| Workflow Events | 50,000 / mes | $0.02 por 1K eventos |
| Workflow Data Written | 1 GB | $0.50 por GB |
| Workflow Data Retained | — | $0.50 por GB-mes |

Un paso normal genera tres eventos (`step_created`, `step_started`, `step_completed`). Las Functions y Queues se cobran aparte. Límites: 25,000 eventos y 10,000 pasos por run (runtime Node.js), payload máximo 50 MB, 2 GB por run, replay máximo 240 s, 1,000 runs creados por segundo; **duración del run y de `sleep`: sin límite**; cada paso individual sigue el límite de Vercel Functions.

Queues y cron: Vercel Queues (beta) es la primitiva de bajo nivel (`send('orders', {...})`, `handleCallback(...)` de `@vercel/queue`); Workflows es la capa recomendada para lógica de varios pasos. Cron Jobs se define en `vercel.json` (Vercel hace un GET a la ruta con user agent `vercel-cron/1.0`); la doc lo marca como legacy y sugiere Schedules (beta). Un endpoint programado puede iniciar un workflow.

**Lo que existe:**

| Capa | Qué ofrece | Dónde |
|---|---|---|

```ts
import { checkBotId } from 'botid/server';
import { NextRequest, NextResponse } from 'next/server';

export async function POST(request: NextRequest) {
  const verification = await checkBotId();

    return NextResponse.json({ error: 'Access denied' }, { status: 403 });

```

**Lo que tienes que construir tú** (no se encontró producto de primera parte):
- Detección de prompt injection, jailbreaks, PII o contenido dañino (equivalente a Model Armor). Opciones: middleware propio, un modelo juez barato, o modelos de moderación servidos por el gateway (por ejemplo `openai/gpt-oss-safeguard-20b` aparece en el catálogo).
- Autenticación y autorización de usuarios en la ruta del agente y en los endpoints de reanudación de hooks (la doc lo deja explícito: "authenticate the reviewer").
- Rate limiting por usuario a nivel de aplicación: la guía del AI SDK lo resuelve con un servicio externo (Upstash Redis + `@upstash/ratelimit`, https://ai-sdk.dev/docs/advanced/rate-limiting); el WAF limita por claves de la request, no por la lógica de tu app.
- Validación de salida de tools y política sobre anotaciones MCP (el SDK no las aplica solo).
- Identidad propia del agente y gobierno centralizado de tools (ver §10).

## 13. Errores comunes y cómo probar sin gastar

### Errores comunes
1. **Copiar código de v5/v6**: `stepCountIs`, `maxSteps`, `parameters`, `system`, `onFinish`, `experimental_telemetry`, `result.toUIMessageStreamResponse()` y `needsApproval` son de versiones anteriores. En v7 varios siguen como alias deprecados con warning, pero no deben enseñarse.
2. **La propia documentación tiene restos**: la página de Chat Platforms usa `result.fullStream` (el nombre actual es `result.stream`), la guía de despliegue en Vercel aún muestra `result.toUIMessageStreamResponse()` y `convertToModelMessages(messages)` sin `await`, y menciona 10 s / 60 s de duración en Hobby cuando la página de límites dice 300 s. Ante la duda, mandan la guía de migración a 7.0 y la página de límites de Vercel.
3. **Olvidar `stopWhen` con `generateText`/`streamText`**: el default es un solo paso; el modelo llama la tool y no responde. Con `ToolLoopAgent` el default es 20.
4. **`WorkflowAgent.stream()` no tiene tope de pasos**: un modelo que sigue llamando tools corre (y cobra) indefinidamente.
5. **CommonJS o Node 18/20**: v7 es solo ESM y exige Node 22+.
6. **`AI_GATEWAY_API_KEY` definida en el proyecto** anula OIDC aunque la key sea inválida.
7. **Token OIDC local vencido** (dura 12 horas): volver a correr `vercel env pull`.
8. **Guardar `ModelMessage` en vez de `UIMessage`**, o cargar mensajes con tools sin `validateUIMessages`.
9. **Confiar en aprobaciones que vienen del cliente** sin `experimental_toolApprovalSecret`.
10. **Olvidar el `await` en `convertToModelMessages(messages)`**: es asíncrona desde AI SDK 6 (codemod `add-await-converttomodelmessages`).
11. **No cerrar el cliente MCP** o usar stdio en producción.
12. **DevTools en producción**: guarda prompts y respuestas en texto plano.
13. **Workflows cayendo al Local World en producción** por no activar el acceso a System Environment Variables; o un `proxy.ts`/middleware que intercepta `/.well-known/workflow/`.
14. **Dejar sandboxes encendidos**: la memoria se cobra aunque la CPU esté inactiva.
15. **Rate limit del WAF no es global**: los contadores son por región.
16. **Fijar proveedores con `only`** elimina el fallback.
17. **Creer que BYOK evita todo cargo**: si tu key falla, el gateway usa las de Vercel y cobra a tus créditos; los budgets no cuentan gasto BYOK.
18. **Arrancar hoy con el paquete `ai-elements`**: queda deprecado a fines de noviembre de 2026; usar la versión de shadcn/ui.

### Cómo probar gastando poco
- Plan **Hobby** (gratis) alcanza para el tutorial: Functions con Fluid (4 h de Active CPU, 360 GB-h, 1M de invocaciones al mes, 300 s por invocación), Workflows (50,000 eventos y 1 GB al mes), Sandbox (5 h de CPU, 420 GB-h, 5,000 creaciones, sesiones de 45 minutos), BotID Basic y rate limiting del WAF.
- **AI Gateway nivel gratuito**: crédito mensual incluido y solo modelos marcados como free tier (https://vercel.com/ai-gateway/models?freeTier=true), con límites más bajos. Al comprar créditos se pasa al nivel pagado y el crédito gratuito mensual deja de aplicar.
- Modelos baratos para ejercicios: `openai/gpt-6-luna` o `anthropic/claude-haiku-5.5` (0.10 / 0.50 por millón). Variantes `-batch` a mitad de precio para trabajo no interactivo.
- **Sin gastar nada**: pruebas con `MockLanguageModelV4` de `ai/test`; Workflows en local (Local World, `npm run dev`); DevTools local para ver pasos y tokens.
- Poner tope: `vercel ai-gateway api-keys create --name my-key --amount 500 --refresh-period monthly` crea una key con presupuesto; además budgets por proyecto en el dashboard y `stopWhen: isStepCount(n)` en todo agente.
- Prompt caching del gateway (`caching: 'auto'`, según la página general de AI Gateway) para pagar la tarifa reducida de lectura de caché en prompts repetidos. No se verificó en qué objeto va la opción.
- AI Gateway se puede usar sin desplegar nada en Vercel (solo hace falta la cuenta para crear la key).
